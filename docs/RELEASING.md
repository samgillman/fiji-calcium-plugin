# Publish an update

The public download is a GitHub Release, not whatever happens to be on `main`. Everyone can use the same latest-download link. Users who subscribe to Releases receive GitHub notifications; installations from version 2026.11.19.4 can show a startup update prompt, and the **Check for updates** button remains available.

## Normal publishing workflow

1. Make the plugin changes in a branch and open a pull request.
2. Choose a higher calendar version in the form `YYYY.MM.DD.N`, for example `2026.11.20.3`. Update `VERSION`, `CalciumRelease.VERSION` in the plugin, the plugin's displayed/logged version strings, and `CHANGELOG.md`. Version validation catches inconsistent plugin version strings.
3. Add a changelog section headed `## VERSION` for the new version. Review the user guide if behaviour changed.
4. Wait for **Checks** to pass, review the changes, and merge to `main`.
5. The merge automatically starts **Publish release**. Wait for the workflow to succeed. It runs regression checks on Linux and Windows, builds the assets, creates a draft, uploads the complete package, and then publishes it as the latest release.

The workflow uses the repository's `GITHUB_TOKEN` with `contents: write`; no personal token or additional secret is needed. A merge with an already-published VERSION passes checks and skips publishing, so documentation-only merges do not make releases. Published releases are never overwritten. Existing drafts or prereleases block publication for manual review; API errors also stop publication. A new version must be higher than the latest release.

Once publishing succeeds, updated installations offer Install update / Later the next time the plugin window opens (unless startup checks are disabled). This is not an instant push to already-open windows. Install update verifies, backs up and replaces the plugin file; restart Fiji after saving work to activate it. Versions before 2026.11.19.6 need the standalone installer run once. The release includes Install_Calcium_Plugin.groovy, generated from the same release/installation code as the plugin, so the bootstrap and in-plugin installer cannot drift.

The ZIP keeps the fixed name `Calcium_Imaging_Fiji_Plugin.zip`, so this URL remains valid:

https://github.com/samgillman/fiji-calcium-plugin/releases/latest/download/Calcium_Imaging_Fiji_Plugin.zip

## Recovery and explicit triggers

The normal merge workflow needs no tag or manual dispatch. If a run fails before publication, fix the cause and rerun it, or use **Actions → Publish release → Run workflow** on `main`. Review an existing draft before retrying; never overwrite a published release.

A matching tag can also trigger the workflow:

```sh
git tag v2026.11.20.3
git push origin v2026.11.20.3
```

The same publishing workflow runs for `v*` tags and checks that the tag matches `VERSION`.

## Local checks and packaging

Requires Java 17 or newer and Python 3.10 or newer. Tests use Groovy 4.0.28, groovy-json 4.0.28, and ImageJ 1.54p. The test runner downloads these version-pinned jars from Maven Central into ignored `build/deps`, or uses matching jars from a `FIJI_JARS` directory you supply. Downloads retry with backoff across Maven Central's two hosts and Google's copy of Central, and each jar must match the SHA-256 recorded in `tools/run_tests.py`, so a busy or failing mirror cannot fail CI on its first refusal or substitute a different file.

```sh
python3 tools/run_tests.py
python3 tools/build_release.py
```

For Step 4 changes, run `python3 tools/embed_analysis.py` after editing the analysis adapter, pinned sources or `web/step4.*`. The script refreshes separate R and browser bundles inside the single plugin file; validation checks their checksums and exact source contents, and rejects either stale bundle. `python3 tools/run_tests.py --analysis-only` installs the managed R runtime and exercises actual Java → R → CSV analysis, cached setup, paths containing spaces, provenance and parity with the pinned SimpleCa functions. CI runs this on Windows, Linux and macOS in addition to the native GUI regressions. Preserve the upstream license and update `analysis/provenance.tsv` whenever intentionally updating pinned upstream sources.

The runtime gate also checks the shared hand-calculated CSV fixtures, native JSON protocol round trips, generic controls and exact timestamp sidecars. Keep those synthetic fixtures tracked under `tests/fixtures/response-protocols`; expected counts must not be generated by the engine being tested. For local adapter work with an existing R/jsonlite installation, set `CALCIUM_TEST_RSCRIPT` to its executable and run `python3 tools/run_tests.py --analysis-portable`. This exercises the real bridge but does not replace managed installation checks on each target platform.

### Local browser acceptance

The page sources are `web/step4.html`, `web/step4.css` and `web/step4.js`. Preserve all three when updating either embedded bundle. The default regression command includes the local server/endpoint checks and, when Node is available, JavaScript syntax validation. These checks are separate from exercising the page in Chromium.

Run the real browser gate after browser or browser/backend integration changes. It needs Node, the Playwright package and its matching Chromium runtime. One reproducible setup on Linux or macOS is:

```sh
npm install --prefix build/browser-runtime --no-save --no-package-lock playwright@1.62.1
node build/browser-runtime/node_modules/playwright/cli.js install chromium
NODE_PATH="$PWD/build/browser-runtime/node_modules" python3 tools/run_tests.py --browser
```

On a Linux CI runner, use `install --with-deps chromium` when system browser libraries are not already installed. On Windows, set `NODE_PATH` to the absolute `build/browser-runtime/node_modules` directory before running the same Python gate. `NODE_PATH` can instead point at an existing compatible Playwright installation.

The gate starts the actual local Step 4 server, drives `tests/browser/step4_page.js` against it, and saves screenshots in `build/web-step4`. It closes the fixture server afterward. Use an ordinary local desktop or CI runner that permits Chromium and loopback sockets; a restricted executor that blocks browser startup cannot establish browser acceptance. Do not report the syntax/server checks as a passing browser run.

For Step 4 acceptance, check the preview before analysis as well as the completed result: **Recording** is the initial view, top playback controls are usable, no result-percentage placeholders appear, and **Static colour overview** remains still with the appropriate disabled controls. Check playback against the selected time base and the clearly labeled fallback when timing is unavailable. Expand the detailed rule and diagnostic sections, then verify that pending edits leave the completed result, its timing and exported provenance unchanged until a successful rerun.

With a desktop display available, `python3 tools/run_tests.py --gui` also exercises the inline Step 1 Install update/Later controls, checks before loading a movie, offline startup, detection details window, resizing/scrolling, image-canvas cell selection and removal, Undo, and rendered outline contrast with the real plugin controls. Release metadata is simulated. CI runs these GUI checks on Windows and on Linux with a virtual display.

The package, standalone plugin file, standalone installer, version file, checksum file, and release notes are written to ignored `dist/`. Tests use a mock Cellpose process and real ROI ZIPs; do a real Fiji/Cellpose smoke test for changes to detection or image measurements.

## Correct a bad release

Keep existing releases available for reproducibility. Make the fix under a higher version and publish again. Users can download an older release from the Releases page and replace their installed script manually if needed. Do not overwrite an already-published tag or asset.
